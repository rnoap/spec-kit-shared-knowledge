# Feature Specification: Context Budget & Trust Model

**Feature Branch**: `005-context-budget-trust`

**Created**: 2026-09-04

**Status**: Draft

**Input**: User description: "Guard de presupuesto de contexto (max_items / max_bytes en el índice). Un corpus grande revienta el contexto del agente; ninguna extensión del catálogo lo hace y sería tu diferenciador. Sección 'Modelo de confianza' en el README: knowledge-config.yml se commitea, así que un PR puede añadir una URL arbitraria que luego se clona. No es ejecución de código, pero merece documentarse."

## Overview

The extension currently tells the agent to read the knowledge index **in full** and then open **every** file it references. That instruction has no upper bound. A project that points at three well-populated repositories with no path filter can produce a corpus of thousands of files, and the agent either exhausts its context window before it reaches the user's actual request or silently drops most of what it was handed. The corpus grows with the team; nothing in the current design pushes back.

This feature gives the corpus a declared ceiling — a maximum number of items and a maximum total size — and makes the extension honour it while stating, out loud, exactly what it left out. Withholding knowledge silently would be the same class of failure the stale index was: an outcome that looks like success.

It also writes down the trust model. `knowledge-config.yml` is a committed, shared file, so a merged pull request causes every developer's machine and every automated environment to fetch a repository chosen by whoever opened it. That is not code execution, and the extension already defends against the parts that would be — but the parts it does *not* defend against have never been stated anywhere a reviewer would look.

## Clarifications

### Session 2026-09-04

- Q: Should a conservative context budget apply by default, or is it strictly opt-in? → A: Strictly opt-in, with an advisory warning when an unbudgeted corpus grows past a documented threshold. A default would be the first time this extension broke the "upgrade and change nothing, observe nothing different" guarantee that the last two releases made explicitly. The warning costs no new concept — synchronization already emits exactly this shape of informational, non-blocking warning when a project configures more than ten sources — and it puts the problem in front of the user at the moment it appears rather than relying on them to have read a changelog.
- Q: Who decides which items survive when the budget binds? → A: The extension, by a fixed documented rule; no configuration influences the order. A user-declarable priority was rejected because setting it correctly requires knowing the size of every source's corpus, which is exactly the thing the user could not see before this feature existed. Reusing path-filter declaration order was rejected because `path_filter` already carries three documented forms and a validation rule, and giving it a second, invisible meaning would make it harder to explain than either mechanism is on its own. A fixed rule can be extended with an optional priority field later without breaking anything; the reverse is not true.
- Q: Does the budget bound only the index, or also what gets fetched and cached? → A: The index only. Bounding the fetch would make a withheld item genuinely unreachable rather than merely un-injected, and would apply inconsistently in practice, because a source whose cache is fresh by policy is served with no fetch at all. The scarce resource this feature exists to protect is the agent's context, not disk. Bounding clone time and disk is a real concern and is recorded as explicitly out of scope rather than left unmentioned.
- Q: What value and unit does the FR-032 advisory threshold have? → A: One fixed, built-in threshold per budgeted dimension — item count and total size — with the applicable value named in the warning text. The requirement justified itself by analogy to the existing "more than ten sources" warning, and that precedent is a fixed built-in count; making this one configurable would ask the user to set a knob whose only purpose is to warn them about a knob they have not set. Two thresholds rather than one because FR-001 makes the two limits independent, so a corpus can hit either wall alone and a single-dimension warning would stay silent for the other.
- Q: How does conflict atomicity interact with per-source allocation, given that a conflicting path spans two sources with separate shares? → A: All versions of a conflicting path are withheld unless every version fits, and the freed capacity is not reallocated. Per-source allocation and "no silent winner" cannot both hold when one side fits and the other does not; preserving the no-silent-winner guarantee is worth more, because a budget that shows the agent one team's version of a contested contract and hides the other is precisely the failure conflict reporting exists to prevent. Capacity is not reused because reuse would make the result depend on how many passes the selection makes, which would break the on-paper predictability FR-007b requires.
- Q: When a per-source limit exceeds the project-wide ceiling, is the source skipped or is the value clamped? → A: Clamped, and the clamping reported. A malformed value has no safe reading, which is why FR-020 skips its source; a well-formed value that merely exceeds the ceiling has exactly one safe reading — the ceiling still binds — so skipping the source would destroy that source's knowledge to punish a redundancy. This follows the same reasoning already recorded for FR-021.
- Q: How does a user find out **which** document was withheld, rather than only how many? → A: Through the existing verbose reporting mode; the default output keeps counts plus individually named exceptions. User Story 2 opens with a developer noticing a specific decision record has stopped being cited, and counts alone do not answer that. The list is kept out of the default output because synchronization runs at up to four automatic points per feature cycle and a list of that size would bury the summary it exists to support. It is kept out of the index for a different reason: naming withheld documents in the one file the agent is told to read invites it to open exactly what the budget excluded.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Bound what the agent is asked to read (Priority: P1)

A developer has configured four knowledge sources. Two of them are large documentation repositories with no path filter. Every automatic sync now produces an index pointing at over a thousand markdown files, and the agent's specs have started to get worse rather than better — it runs out of room before it reaches the feature description. The developer declares a context budget in the project configuration, and from the next sync onward the index references only as much knowledge as the budget allows.

**Why this priority**: This is the failure the feature exists to prevent, and it is the only part that changes what the agent actually receives. Without it, nothing else in this feature has an effect.

**Independent Test**: Configure a corpus that substantially exceeds the budget, sync, and confirm the resulting index references no more than the configured number of items and no more than the configured total size — and that this holds on a repeat run.

**Acceptance Scenarios**:

1. **Given** a project with a context budget configured and a cached corpus that exceeds it, **When** synchronization runs, **Then** the written index references a subset that fits inside both the item and the size ceiling.
2. **Given** the same project and the same cached content, **When** synchronization runs a second time, or runs on a different developer's machine, **Then** the index selects the same subset.
3. **Given** a project with no context budget configured, **When** synchronization runs, **Then** the index contains exactly what it would have contained before this feature existed.

---

### User Story 2 - See what was withheld, and why (Priority: P1)

The same developer notices the agent no longer cites a decision record it used to cite. Rather than reading the cache directory by hand to work out what happened, they read the synchronization output and the index header, both of which state how many items and how much content were withheld, and from which sources.

**Why this priority**: Equal to Story 1, and inseparable from it. A budget that trims the corpus without saying so converts a visible context overflow into an invisible knowledge gap — the user would have no way to tell the difference between "this decision was never configured" and "this decision was dropped to fit". Shipping the guard without the report would make the extension less trustworthy, not more.

**Independent Test**: With a binding budget, confirm the output and the index each state the withheld item count and withheld size, broken down per source, and that the numbers reconcile with the cached corpus.

**Acceptance Scenarios**:

1. **Given** a budget that excludes some items, **When** synchronization completes, **Then** the summary states how many items were withheld and how much content they represent, per source.
2. **Given** a budget that excludes some items, **When** the index is read, **Then** it carries the same statement, so a consumer that only ever sees the index still knows the corpus is partial.
3. **Given** a budget that excludes some items, **When** the agent-facing context instructions are emitted, **Then** they state that the corpus is partial, so the agent does not present it as the project's complete knowledge.
4. **Given** an item excluded from the index, **When** the user searches the knowledge corpus for it, **Then** it is still found — the budget governs what is injected automatically, not what exists.

---

### User Story 3 - Understand what merging a config change grants (Priority: P2)

A reviewer receives a pull request that adds one line to `knowledge-config.yml`. They open the project README, find the trust model section, and can answer three questions without reading the extension's source: what will happen on their machine once this merges, what is and is not executed, and what the extension does not protect them from.

**Why this priority**: Documentation-only, so it changes no behaviour and can ship independently — but the exposure it describes exists today and is currently undocumented. A reviewer who does not know that a config line causes a fetch on every teammate's machine has no reason to treat that line as security-relevant.

**Independent Test**: Give the README to someone who has not read the extension's source and ask them what merging a one-line configuration change causes; the section is sufficient if they can answer without further reference.

**Acceptance Scenarios**:

1. **Given** the README, **When** a reader looks for the security posture of a committed configuration, **Then** they find a trust model section that names the specific exposures and the specific defenses.
2. **Given** a reader editing `knowledge-config.yml` directly, **When** they read the configuration template's comments, **Then** they are pointed at the trust model rather than having to know it exists.
3. **Given** the trust model section, **When** a risk is described as defended, **Then** the defense named is one the extension actually applies today.

### Edge Cases

- **A single item is larger than the entire budget.** It can never be included, and a rule that quietly skips it makes the budget look broken. It must be excluded and named, with its size, so the user can act.
- **The budget is smaller than the number of enabled sources.** There is not enough room to give every source even one item. The outcome must be documented rather than emergent, and must not depend on the order sources happen to appear in the file.
- **Two versions of a conflicting path fall on opposite sides of the budget line.** Conflict reporting exists to avoid a silent winner. A budget that keeps one version and drops the other would manufacture exactly that, so every version is withheld unless all of them fit (FR-033).
- **A per-source limit is set higher than the project-wide ceiling.** The value is well-formed and its meaning is unambiguous, so it is clamped rather than treated as an error (FR-003a). Only a value that cannot be interpreted at all costs a source its place.
- **The budget is configured but the corpus fits inside it.** Nothing should be withheld and nothing should be reported as withheld — a non-binding budget must leave the index indistinguishable from no budget at all, apart from the generation timestamp every sync writes.
- **The budget value is malformed** — a negative count, a size with no unit, a value arriving by hand-edit or by pull request. Behaviour must be defined, and must not be "strip all knowledge".
- **A source contributes zero items** because it is empty or its path filter matches nothing. It must not be reported as having been withheld by the budget.
- **All sources are unreachable and the index is served from cache.** Whether the budget still applies must be defined; the corpus being read is the cached one either way.

## Requirements *(mandatory)*

### Context budget — declaration

- **FR-001**: The configuration MUST support a maximum item count and a maximum total content size for the knowledge corpus the index exposes. Both MUST be optional and independent — a project may declare either, both, or neither.
- **FR-002**: Both limits MUST be settable project-wide and settable again per source, occupying the same two positions in the configuration file as the cache freshness policy so that one file does not carry two different scoping *shapes*. The *semantics* differ deliberately and MUST NOT be inferred from that precedent: a per-source freshness value **replaces** the project value, whereas a per-source budget only **lowers** it (FR-003).
- **FR-003**: A per-source limit MUST bound that source's own contribution. It MUST NOT raise the project-wide ceiling — the project-wide value is the total the agent will be asked to read, and no per-source setting may exceed it.
- **FR-003a**: A per-source limit larger than the project-wide ceiling MUST be clamped to that ceiling and the clamping MUST be reported. It MUST NOT cause the source to be skipped. The value is well-formed and has exactly one safe reading, so skipping would destroy that source's knowledge to punish a redundancy — the same reasoning that governs a malformed project-wide limit.
- **FR-004**: When neither limit is configured, the index MUST contain exactly what it contains today. The budget is opt-in and no default value is applied — see FR-032 for how an unbudgeted project is told it needs one.
- **FR-005**: The configuration schema version MUST remain unchanged, as every field introduced here is optional.

### Context budget — enforcement

- **FR-006**: When the corpus exceeds an effective limit, the index MUST reference only a subset that fits within **both** the item ceiling and the size ceiling.
- **FR-007**: Selection MUST be deterministic. The same configuration applied to the same cached content MUST produce the same subset on every run and on every machine. A committed configuration that yields a different corpus per developer would make cross-repo context unreproducible and any resulting spec unexplainable.
- **FR-007a**: The selection rule MUST be fixed and owned by the extension — no configuration value may influence which items are chosen. Where a project-wide ceiling applies, the rule MUST allocate it in equal shares across the enabled sources that have items and MUST release any share a source does not need to the remaining sources; where only per-source ceilings are declared, each source is bounded by its own and no allocation is required. Within a source, items MUST be taken in ascending order of relative path. The rule MUST NOT depend on filesystem enumeration order, on the order sources appear in the configuration file, or on the order in which sources were synchronized.
- **FR-007b**: The selection rule MUST be documented in the project's user-facing documentation, in enough detail that a user can predict which items their configuration will yield from the contents of their own repositories. A deterministic rule the user cannot reproduce on paper is indistinguishable from an arbitrary one.
- **FR-008**: When the project-wide budget binds, no enabled source that has items available MAY be reduced to zero while another source receives more than its equal share. Starvation caused by the order sources are declared in is prohibited outright — it would be invisible in the configuration file and would make the corpus a function of where a line was inserted.
- **FR-008a**: Where the item ceiling is smaller than the number of enabled sources with items available, some sources must receive nothing by arithmetic. In that case the sources that receive nothing MUST be selected by the same deterministic rule as everything else, and MUST be named individually in the withholding report — a source contributing nothing is the outcome a user is least likely to expect and most likely to misread as a broken configuration.
- **FR-009**: An item that cannot fit within the effective size ceiling on its own MUST be excluded and reported by name and size. It MUST NOT block or consume the budget available to other items.
- **FR-010**: Size MUST be measured over the content the agent is instructed to read, not over the index document that references it. The budget exists to bound the agent's context, and the index itself is a small fraction of what that instruction pulls in.
- **FR-011**: Enforcement MUST apply to the corpus being indexed regardless of how each source's content was obtained — freshly fetched, served from a policy-fresh cache, or served from a stale cache after an unreachable source. The agent reads the same index in all three cases.
- **FR-012**: No command-line flag MAY raise or bypass the budget. The automatic synchronization points are exactly where a context overflow does the most damage, and a bypass reachable from them would defeat the guarantee.
- **FR-012a**: The budget MUST bound only the corpus the index exposes. It MUST NOT change which content is fetched or which content is cached: every item a source contributes stays on disk and stays reachable, so a withheld item is un-injected rather than unavailable.
- **FR-033**: Where a path is reported as a conflict between sources of differing repository identity, its versions MUST be included or withheld as a unit. Each version is charged against its own source's allocation; where any version does not fit, **every** version of that path MUST be withheld. The capacity freed by such a withdrawal MUST NOT be reallocated to other items, because reuse would make the outcome depend on how many passes the selection makes and would break the on-paper predictability FR-007b requires. The withdrawal MUST be reported as a single conflict withdrawal, not as unrelated per-source exclusions. A source left with no items by such a withdrawal MUST be named in the report in the same way as a source that received no allocation — the user needs to know it contributed nothing, and the mechanism that emptied it is not something they can infer.

### Context budget — reporting

- **FR-013**: When any item is withheld, synchronization MUST report the withheld item count and withheld content size, broken down per source, and MUST state the limit that produced the outcome. A reported reduction must never be unexplained.
- **FR-014**: The index itself MUST carry the same statement, so that a consumer reading only the index can tell the corpus is partial without access to the command output that produced it. The index MUST NOT name the withheld items individually: naming them in the one document the agent is instructed to read would invite it to open exactly the files the budget excluded.
- **FR-015**: When any item is withheld, the agent-facing context instructions MUST state that the corpus is partial, so the agent does not present it as the project's complete knowledge.
- **FR-016**: When a budget is configured but nothing is withheld, no withholding MUST be reported, and the index MUST carry no withholding fields and no partial-corpus marker — leaving it indistinguishable, apart from the generation timestamp every sync writes, from the index produced with no budget configured.
- **FR-017**: Items excluded from the index MUST remain findable through the knowledge search command. The budget governs what is injected automatically into an agent's context; it does not govern what the project knows.
- **FR-035**: The search command MUST take its inventory from the complete per-source item records rather than from the agent-facing index. Search and the index have different audiences — the index is bounded because an agent reads all of it, whereas a search returns only what a query matched — so binding search to the budgeted index would make FR-017 unsatisfiable by construction. The same complete records MUST be what FR-034's withheld list is derived from.
- **FR-018**: The status command MUST display each source's contribution against its effective limits, and MUST name the limit being applied — mirroring the existing requirement that a reported freshness state always states the threshold that produced it.
- **FR-032**: When no budget is configured and the corpus exceeds a documented advisory threshold, synchronization MUST emit an informational warning that states the corpus size and points at the budget settings. The warning MUST NOT alter the index, MUST NOT withhold anything, and MUST NOT prevent the command from completing successfully — it has the same standing as the existing warning emitted when a project configures an unusually large number of sources. Without it, the projects that most need a budget are precisely the ones that will never learn one exists.
- **FR-032a**: There MUST be one advisory threshold per budgeted dimension — item count and total size — so that a corpus hitting either wall alone is still reported. Each MUST be a fixed built-in value rather than a configurable one, and the warning MUST name both the threshold it applied and the measured value that crossed it, so the user can judge the recommendation against their own corpus rather than taking it on trust.
- **FR-034**: The identity of every withheld item MUST be obtainable on demand through the existing verbose reporting mode. The default output MUST NOT list them individually — synchronization runs at up to four automatic points per feature cycle, and a list of that size would bury the summary it exists to support — but a user who needs to know which specific document was withheld MUST be able to find out without inspecting the cache directory by hand.

### Context budget — validation and compatibility

- **FR-019**: The item and size limits MUST each be checked against a documented rule for their field **each time the configuration is read**, extending the existing read-boundary validation rather than introducing a second, write-only convention.
- **FR-020**: A malformed **per-source** limit MUST skip only its own source, naming the field and the offending value, with every other source still processed and the command still completing successfully. This governs values that cannot be interpreted at all; a well-formed value that merely exceeds the project-wide ceiling is governed by FR-003a and MUST NOT cost the source its place.
- **FR-021**: A malformed **project-wide** limit MUST be reported and treated as though it were not configured. Failing to a zero budget would strip every source's knowledge on the strength of one typo; failing open preserves availability and is consistent with the existing rule that a cache is served even when its freshness policy cannot help.
- **FR-022**: All commands MUST continue to report failures as messages rather than process errors, on every path introduced here.
- **FR-023**: A project upgrading to this version without changing its configuration MUST observe unchanged behaviour.

### Trust model documentation

- **FR-024**: The README MUST carry a trust model section describing the security posture of a committed, shared `knowledge-config.yml`.
- **FR-025**: The section MUST state explicitly that merging a configuration change causes the referenced repository to be fetched on every machine and automated environment that subsequently runs a synchronization — including via the automatic hooks, which the reviewer of that change may never invoke themselves.
- **FR-026**: The section MUST enumerate the specific exposures that follow, at minimum: that a configured location receives a network request from every such machine; that the local version-control credential mechanism may present credentials to a host chosen by the configuration; that fetched documents enter the agent's context as untrusted input that the extension does not inspect or sanitize; and that a fetched document may be a symbolic link, which the extension neither resolves nor rejects, so a source can cause a file outside its own repository to be read into the agent's context.
- **FR-027**: The section MUST state clearly what does **not** happen — that fetched content is read as data and is never executed, and that the extension does not run build steps, scripts, or repository hooks from a source.
- **FR-028**: The section MUST name the defenses the extension actually applies today and MUST be explicit about which of the enumerated exposures each one does and does not cover. A defense listed without its limits reads as a guarantee the extension does not make.
- **FR-029**: The section MUST give reviewer guidance identifying a change to this configuration file as security-relevant, and stating what to check before approving one.
- **FR-030**: The configuration template MUST point readers at the trust model, so that someone editing the file directly encounters it without needing to know it exists.
- **FR-031**: The trust model MUST NOT describe any defense the extension does not currently implement. If a mitigation is desirable but absent, it MUST be described as absent.

### Key Entities

- **Context budget**: A declared ceiling on the knowledge corpus the index exposes, expressed as a maximum item count and a maximum total content size. Held at project scope and optionally at source scope; absent by default.
- **Effective limit**: The limit that actually applies to a given source, per dimension — the **lower** of its own declared value (where set) and its share of the project-wide ceiling. Preferring the source's own value over its share would let the total exceed the project ceiling: with a ceiling of 120 across three sources, a source declaring 60 against a 40 share would push the total to 140. Unlike the existing cache-age policy, whose per-source value *replaces* the project value, a per-source budget is a sub-ceiling — it can only lower what a source contributes, never raise it. This is the value that must appear in any report explaining an outcome.
- **Withholding report**: The record of what the budget excluded — counts and sizes per source, plus any individually oversized item named on its own. Surfaced in four places with deliberately different content in each: the default command output, the verbose command output, the index, and the agent-facing instructions.
- **Trust model statement**: The README section describing what a committed configuration grants, what the extension defends against, and what it explicitly does not.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: With a budget configured and a cached corpus that exceeds it, the index references no more items and no more total content than the budget allows, on every run.
- **SC-002**: The same configuration and the same cached content select the same items, in the same order, on two different machines — the two indexes differing only in their generation timestamp and in machine-local cache paths, neither of which is knowledge — so a spec generated from cross-repo context can be explained by the configuration alone.
- **SC-003**: When the budget binds, a user can determine how many items and how much content were withheld, and from which sources, from the command output alone — without inspecting the cache directory. The same statement is present in the index and in the agent-facing instructions, so no consumer of the corpus can mistake a partial one for complete.
- **SC-004**: A project that upgrades and configures no budget keeps its existing configuration valid with no edits, and produces the same indexed item set and the same agent-facing output as before the upgrade.
- **SC-005**: When the project-wide budget binds across multiple sources, every enabled source that has items available contributes at least one — unless its own per-source limit prevents it, or the item ceiling is smaller than the number of such sources, in which case every source receiving nothing is named in the output.
- **SC-006**: An item withheld from the index is still present in the cache and is still returned by a search that matches it — the search result set is unaffected by the budget.
- **SC-007**: Two conflicting versions of the same path are either both present in the index or both absent from it — the budget never selects a winner between them — and an absent pair is reported as a single conflict withdrawal rather than as two unrelated exclusions.
- **SC-008**: Every command exits successfully on every path exercised here, including a budget smaller than a single item, a budget smaller than the source count, and a malformed limit value arriving by hand-edit or pull request.
- **SC-009**: A reader of the README who has not read the extension's source can state what merging a one-line configuration change causes to happen on their machine, what is and is not executed, and at least one exposure the extension does not defend against.
- **SC-010**: A reviewer approving a change to `knowledge-config.yml` has a stated set of checks to perform, located in the project's own documentation rather than inferred.
- **SC-011**: A configured budget that the corpus does not exceed produces an index and command output indistinguishable — apart from generation timestamps — from the same project with no budget configured: no withholding fields, no partial-corpus marker, no withholding lines.
- **SC-012**: The budget holds on every path that produces an index — freshly fetched content, content served from a policy-fresh cache, and content served from a stale cache after an unreachable source — and no available flag or automatic invocation produces an index that exceeds it.
- **SC-013**: The status command reports each source's contribution against the limit applied to that source, and names the limit, so a reported contribution is never unexplained.
- **SC-014**: Every defense named in the trust model corresponds to behaviour the extension applies today, and every exposure it names as undefended has no defense claimed against it.
- **SC-015**: A project with no budget configured whose corpus has grown past the advisory threshold learns so from an ordinary synchronization, and the index that synchronization produces is identical to the one it would have produced without the warning.
- **SC-016**: Given a configuration and the contents of the source repositories, a user can predict the exact set of items the index will contain without running the command.
- **SC-017**: The advisory warning names both the threshold it applied and the measured value that crossed it, for whichever dimension triggered it, so a user can judge the recommendation against their own corpus rather than taking it on trust.
- **SC-018**: A conflicting path whose versions cannot all fit contributes none of them, and the capacity that frees is not given to other items — so the same configuration and content yield the same index no matter how the selection is executed.
- **SC-019**: A per-source limit larger than the project-wide ceiling leaves that source contributing normally under the ceiling, with the clamp reported; only a value that cannot be interpreted at all costs the source its place.
- **SC-020**: A user who knows a specific document has stopped appearing can obtain its path from the tooling, without inspecting the cache directory by hand — while the default output of an automatic synchronization stays short enough to read, and the index names no withheld item at all.

## Assumptions

- **The budget bounds the agent-facing corpus, not the project's knowledge.** The extension's scarce resource is the agent's context window, not disk. Everything cached remains reachable through search; the budget only governs what the automatic instructions tell the agent to read. Conflating the two would turn a context guard into knowledge deletion.
- **Size is expressed as a human-readable value with an explicit unit**, following the precedent already set by the cache freshness duration, so that a committed configuration is unambiguous to a reader who did not write it.
- **Both limits are optional and independent.** A project that only ever hits the file-count wall should not have to reason about bytes, and vice versa. Requiring both to be set would make the feature harder to adopt than the overflow it prevents.
- **A per-source limit is a sub-ceiling, never an escape hatch.** The freshness policy's per-source value *replaces* the project value, which is correct there — one source may legitimately be refreshed less often than the rest. A budget is different in kind: the project-wide value is the total the agent will be asked to read, so a per-source value that could exceed it would make the project-wide number meaningless. The two settings share a shape but not a semantic, and this specification states the difference rather than letting a reader infer the wrong one from the precedent.
- **Determinism matters more than optimality.** A selection rule that picks a marginally better subset but varies with filesystem enumeration order would be worse in practice: the configuration is committed and shared, so two developers with identical configuration must receive identical context or the resulting specs cannot be compared.
- **Determinism is a property of the selection, not of the bytes on disk.** The index carries a generation timestamp, and the cache paths it links to are derived from each machine's own source locations, so two correct runs never produce byte-identical files. Every claim of sameness in this document is therefore a claim about **which items were selected and in what order** — the only part a configuration can determine, and the only part that is knowledge. Verification must compare item sets, never raw file bytes.
- **Items are taken in path order rather than smallest-first.** Smallest-first would fit more items inside the same size ceiling, which is the better answer if the only goal is maximising item count. It is the worse answer for a shared configuration: adding one large file to a source silently changes which unrelated small files survive, so no user can predict the corpus from their own repository. Path order localises the effect of any change — adding a file can only affect what comes after it — which is what makes FR-007b achievable at all.
- **Bounding what is fetched and cached is out of scope.** Clone time and disk are real costs and this feature does not address them; `path_filter` remains the only lever for both. A fetch bound was rejected here because it would make a withheld item unavailable rather than merely un-injected, and because it would apply inconsistently the moment a cache freshness policy is also configured — a source served from a policy-fresh cache performs no fetch for the bound to govern. Recording it as out of scope is preferable to silence, so that a later reader does not mistake the omission for an oversight.
- **The advisory warning reuses an existing shape rather than introducing a concept.** Synchronization already emits an informational, non-blocking warning when a project configures an unusually large number of sources, and continues normally. FR-032 is the same mechanism pointed at a different measurement, which is why an opt-in budget does not leave the stated problem unsolved for users who never enable one.
- **Capacity freed by a conflict withdrawal is deliberately wasted.** When all versions of a conflicting path are withheld under FR-033, the room they would have occupied is not given to other items. Reusing it would fit marginally more knowledge, but the result would then depend on how many passes the selection makes over the corpus — and a rule whose output changes with its own iteration count cannot be reproduced on paper, which is the whole point of FR-007b. Predictability is bought here at a measurable and deliberately small cost.
- **Withheld items are named on demand but never in the index.** The two exclusions have different reasons and should not be read as one policy. They are absent from the default output because it runs at four automatic points per feature cycle and must stay readable; they are absent from the *index* because the index is the one document the agent is instructed to read in full, and listing the excluded files there would invite it to open precisely what the budget removed. Verbose mode carries the list, which is where the existing per-source file listing already lives.
- **Silent truncation is the failure mode to avoid.** This mirrors the reasoning already recorded for deleting the index when no sources remain — an agent presenting a partial corpus as complete is a silent failure that looks like success. Every requirement here that concerns reporting exists for that reason, which is why the withholding report is a P1 story rather than a polish item.
- **Validation follows the read boundary already established.** Configuration reaches a project by hand-edit, by pull request, and from older versions of the extension. A new field validated only on write would be unchecked on all three routes, and would be the only field in the file with that gap.
- **Project-wide and per-source validation failures are treated differently on purpose.** A per-source failure has a natural blast radius — its own source. A project-wide failure does not, so it fails open rather than reducing every source to nothing. This asymmetry is stated because it is not obvious, and because the opposite choice is defensible right up until one typo empties the corpus.
- **The trust model is documentation, not a new mechanism.** The exposures described already exist. The defenses described — rejecting option-shaped configuration values, separating arguments to the version-control tool, fetching without checking out arbitrary content, bounded timeouts, path filters, and hooks the user can decline — are already implemented. This feature does not add a defense; it stops the posture from being something a reader has to reconstruct from the source.
- **Prompt injection through fetched content is named as an exposure, not solved here.** Sanitizing untrusted markdown before it reaches an agent is a substantial problem with no reliable general answer, and pretending otherwise in a trust model would be worse than the current silence. It is documented as undefended so that a reader weighing a new source knows what they are accepting.
- **Symlink following is named as an exposure, and is the strongest candidate for the next feature.** Planning research found that indexing enumerates `.md` files after checkout, and that a source repository containing a symbolic link to a file outside itself — a private key, a credentials file — produces an index entry the agent is instructed to open, from which the contents could reach a committed specification. Refusing to index links that escape the cache root is a small fix, but it is a behavioural change with its own edge cases, and this feature's trust-model half was deliberately scoped as documentation. Naming it as undefended is what FR-031 requires; omitting it because it is inconvenient is the exact failure FR-031 was written to prevent.
- **Two requirements were added after this specification was clarified.** FR-035 and the symlink clause in FR-026 came from planning research, not from drafting or clarification. FR-035 follows through on a consequence of FR-017 that the original text left implicit — the search command reads the index, so a budgeted index would have made "withheld items stay findable" false by construction. They are recorded here so this document remains the complete description of what ships.
- **The two capabilities ship together.** They are the same concern seen from two angles: what an uncontrolled corpus does to the agent, and what an uncontrolled configuration grants to whoever edits it. The budget bounds the blast radius; the trust model explains why the radius exists at all.
